# AI 应用让用户自带额度：从 Pollinations 的授权模式谈接入设计

资料核实：2026-10-15。类型：常青教程与项目分析。没有执行登录授权、充值或付费 API 测试；本篇也不表示 CodingRouter 已提供同类功能。

开发 AI 应用时，开发者承担所有调用费是一种模式，让用户授权使用自己的平台额度是另一种。选择哪种方式，需要同时考虑试用门槛、费用归属和授权体验。对于售卖 API 的服务方，理解这种区别有助于更准确地判断客户究竟在购买模型能力、应用服务，还是一套接入机制。

## 官方方案解决了什么问题

Pollinations 的 Connect User Wallets 文档介绍了用户授权应用使用自身 Pollen 额度的流程。它区分可公开的 App Key 和授权后用于调用的用户凭据，并为新网页集成介绍授权码加 PKCE 的方式。具体字段、默认值和限制应以当期官方文档为准。[官方说明](https://github.com/pollinations/pollinations/blob/main/BRING_YOUR_OWN_POLLEN.md)

这类设计把应用身份与用户调用授权分开。用户授权完成，不等于应用获得无限额度；应用仍需要处理授权范围、预算、到期和撤销。不要把“使用用户额度”宣传成模型调用免费，费用只是有了不同的承担方。

## 用户界面应说明哪些事情

下面是基于该模式的产品建议，不是官方功能清单。授权前解释应用准备做什么、将调用哪类模型，以及由谁承担费用。授权后显示是否可用，在额度不足、凭据过期或权限被撤销时提供明确的恢复路径。用户不应通过公开 Issue 上传自己的凭据来完成排错。

接入时需要校验回调与请求的对应关系，并依照官方说明处理授权码和凭据。用户取消授权也属于正常路径，应返回应用并说明下一步，不能把它当作需要反复重试的服务故障。

## API 服务方可以借鉴什么

接触客户时，先问清楚客户想自付调用费、让终端用户自付，还是由企业集中结算。不同模式影响账户体系、客服流程和账单解释，也影响样例项目应怎样组织。当前是否支持某种模式，需要根据服务实际能力回答，不能只凭行业案例作出承诺。

## 可继续开发的项目

可以先制作不连接真实账户的授权流程演示，覆盖同意、取消、到期和额度不足四种状态，明确标注演示数据。确认需求后再实现真实接入；当前仓库尚未提供授权代码。
