# 重试能救一次请求，也可能拖垮整条任务：模型 API 失败后怎么处理？

Decide when to stop, retry or fall back using a shared time and attempt budget.

资料核实：2026-10-19（北京时间）。类型：排错教程。本文为官方文档解读与设计建议，未执行线上或付费 API 测试，不表示 CodingRouter 已支持文中第三方功能。

给 SaaS 或 Agent 加重试时，可能出现这样的取舍：请求最终成功了，用户却已等不及；工具再次执行，还可能重复创建工单。本文帮助你决定何时等待、停止或回退，并给整条任务设边界。

## 一个近期案例

Anthropic 在 2026-10-15 宣布 Claude Opus 5.5 Fast mode 退出研究预览。官方文档说明，高速档有独立限流，触发时返回 429 与 Retry-After；SDK 也可能自动重试。继续等高速容量，还是允许回到标准档，是截止时间、体验与费用条件的取舍，不是无限重发就能解决。该事件不是今天的新公告。

## 先判断失败发生在哪

下面是设计决策表；具体状态和字段以实际供应商为准。

| 看到的情况 | 建议动作 | 必须保留的边界 |
| --- | --- | --- |
| 参数、身份、权限或余额问题 | 先修请求或账户状态 | 条件没变就不要盲目重发 |
| 限流且给出等待提示 | 比较建议等待与任务剩余时间 | 超出截止时间则结束或明确排队，不提前抢试 |
| 暂时服务错误或连接中断 | 预算内有限重试 | 先确认前次是否已执行、能否安全重放 |
| 已有部分流式输出 | 标记未完成，按业务规则处理部分结果 | HTTP 成功不代表完整；不要自动拼接两次生成 |
| 工具已执行而回包丢失 | 先查业务动作记录 | 有去重或幂等机制才能安全恢复 |

## 给整条任务统一预算

先确定用户能接受的总等待，再分配单次超时、等待间隔与总尝试次数。把 SDK、网关和业务代码各自的重试都算进去：任一层耗尽任务预算，外层不能重新开始一套循环。

回退必须预先约定。切换模型或速度档位可能改变费用、结果格式、工具能力与缓存条件。先限定可用替代方案和质量要求，再记录实际选择，不能悄悄换模后仍声称原配置完成。

例如，任务剩余时间已短于服务端建议等待，就应选择结束、明确排队，或使用预先允许的替代方案；“再试一下”不是独立于预算的免费机会。这是判断示例，不是性能测试结果。

## 怎样知道策略有用

先用合成任务记录：任务号、错误类型、部分输出或外部动作、累计等待、尝试次数、最终结果。检查“正确停止、有限恢复、避免重复动作”，不要只看最终成功数。错误日志须脱敏，部分内容也需按业务规则决定是否保留。

常见失败是只看状态码、叠加多层重试、把超时当作从未执行。预期结果应是失败路径可追踪、等待和费用可解释；本文不提供已实测重试器，也不承诺自动恢复所有故障。真实 API 测试应另设明确预算。
