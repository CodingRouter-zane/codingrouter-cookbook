# 策略已经拒绝，旧审批签名为什么还能让工具执行？AI SDK 7.0.178 升级检查

*An approval signature proves issuance—not every authorization decision.*

如果你的 Agent 能改数据库、发消息或扣款，又把消息历史交给客户端保存，“策略已拒绝”不一定等于“这次动作永远不能执行”。本文帮助使用 AI SDK 签名审批的团队完成版本、历史请求和密钥轮换检查；客户场景是编辑假设，不是实际事故反馈。

## 已核实：升级代码，不会自动撤销旧签名

Vercel 于北京时间 **2026-11-21** 发布 `ai@7.0.178`。官方说明：启用 `experimental_toolApprovalSecret` 时，原实现会给策略自动拒绝的请求签名。能控制消息历史的客户端可能把它配上“已批准”响应送回；若重新计算策略所用的历史也由客户端决定，原本拒绝的工具仍可能执行。

修复让自动拒绝请求不再带签名；伪造的批准在执行前以 `AI_InvalidToolApprovalSignatureError` 拒绝。上游提交说明覆盖 `generateText`、`streamText` 和 `ToolLoopAgent`；等待人工批准的请求仍会签名，`WorkflowAgent` 在该提交中没有改变。

**旧版本已经签发的自动拒绝签名仍有效。** 官方要求轮换审批密钥来撤销它们；代价是正常待审批请求也要重新发起。

## 先判断自己落在哪条路径

| 现场情况 | 应采取的动作 |
| --- | --- |
| 使用上述签名审批，历史由客户端回传 | 优先核对部署产物与修复，检查历史签名 |
| 已部署含修复版本，但仍沿用旧密钥 | 不把“升级完成”当作旧签名已经失效 |
| 没有配置审批密钥，或使用其他版本分支 | 单独审核授权设计；不据此断言安全或套用受影响版本 |
| 工具在供应商侧执行 | 另查供应商审批边界；本地 `toolApproval` 不控制其执行 |

不要把所有早于 7.0.178 的版本一概判为受影响；本次资料未确定完整起始版本区间。

## 建议：把撤销和业务恢复一起上线

1. **盘点真实版本。** 记录 lockfile、构建产物和各执行入口，确认部署版本包含本次修复，不用“已更新 latest”替代证据。
2. **暂停高风险续跑。** 对涉及副作用的待执行动作先冻结或要求重新确认。用服务端可信的预算、资源归属与权限重新校验，不只相信客户端历史。
3. **协调轮换。** 更新签名和验签实例，确认旧密钥不再被接受；不要为了兼容在验签端继续接受旧签名。预告待审批请求失效，重新请求合法批准。
4. **保留回退边界。** 若正常审批恢复失败，保持暂停、修复流程；不要回退到旧密钥或关闭签名校验来“恢复可用”。

示例取舍：一个模拟预算策略已拒绝第二次扣款，用户随后点了“同意”。签名只能证明请求由服务端签发，不能替代当前权限与可信预算校验。轮换不是优化体验的功能，而是撤销历史授权材料的操作。

## 免费验收清单与预期结果

仅在自有隔离环境使用 synthetic 历史和 mock 执行回调，不连接支付、数据库或模型 API：

- 自动拒绝后再回传批准：明确拒绝，mock 执行次数为 **0**。
- 旧密钥签发的请求：轮换后拒绝，不因客户端保留历史而恢复。
- 新密钥下的合法人工批准：按策略执行一次；重复提交由业务幂等保护处理。
- 合法拒绝后的普通会话：可以继续，不应被误当成新批准。

这些是建议的验收条件，不是本文已完成的测试结果。上线前需自行保存版本、脱敏审批 ID、错误类型和执行计数；不要记录密钥或客户消息原文。
