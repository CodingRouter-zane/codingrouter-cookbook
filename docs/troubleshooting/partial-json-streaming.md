# 流式 JSON 只到负号，为什么不能马上判坏？别让半成品覆盖最终结果

*Partial JSON is a progress signal, not a business result.*

如果你的 AI 应用边生成边渲染表格、坐标、金额或工具参数，一个数据块停在 `{"values":[-` 时，你会把它判成坏 JSON、清空页面，还是继续等待？读完本文，你可以把“流式预览”和“可提交的最终对象”分开，避免一次正常的分块让 UI 闪空、任务误失败或半成品进入业务系统。

## 已核实事实：这次坏掉的可能只是片段

Vercel 于 2026-10-30 发布 AI SDK `7.0.158`。官方修复说明指出：当数组第一个负数的流式片段恰好结束在负号，例如 `{"values":[-`，此前的部分 JSON 修复逻辑会得到不可解析结果。对应 PR 说明，这种边界可能让 UI 流中的工具输入暂时变回 `undefined`、让 `useObject` 在一次更新中变成 `undefined`，或让结构化输出跳过该次 partial update。

关键区别是：`[-` 不是合法的**最终 JSON**，但它可以是正常的**中间片段**。官方文档也明确，`streamText` 的 partial output 尚未完整，不能按最终 schema 验证；完整 output 才执行完整验证。这个补丁不等于所有 JSON 错误都应忽略，也不能证明其他 SDK、Provider 或 CodingRouter 接口存在同一问题。

## 真正的冲突：即时反馈与业务正确性

边生成边显示能降低用户等待感，但越早把片段当结果，越容易把短暂状态扩散到缓存、数据库或工具执行。建议把三种状态分开：

| 状态 | 可以做什么 | 不该做什么 |
| --- | --- | --- |
| partial | 显示“生成中”，更新无副作用的预览 | 写入最终记录、计为成功、触发工具 |
| complete | 通过最终 JSON 与 schema 校验后提交 | 只因 HTTP 200 或连接结束就默认成功 |
| error / abort | 保留脱敏诊断，明确标记未完成 | 把最后一个 partial 冒充完整结果 |

工程判断不是“宽松解析还是严格解析”二选一，而是：**中间过程允许不完整，最终提交仍然严格。**

## 一套可复查的处理方法

1. **记录实际版本。** 核对 lockfile 与部署产物，不用 `latest` 代替证据。若使用 AI SDK 7.0 且依赖结构化流，先判断是否早于 `7.0.158`。
2. **分开三份状态。** 原始片段只进短期缓冲；partial object 只用于预览；只有完成事件后的 validated object 才能进入业务层。
3. **不要用一次解析失败清空稳定 UI。** 当前片段不可解析时，保留“生成中”状态或最后一个已确认的预览，并记录 `partial_pending`，不要立刻覆盖成空值。
4. **把副作用放到完成门后。** 写数据库、发送消息、计算价格或调用工具，都应等待完成标记和最终 schema 校验；失败或中止必须保持不可提交。
5. **分类统计，而不是只记 JSON error。** 至少区分：等待更多片段、最终 JSON 非法、schema 不匹配、流中止。否则正常分块会和真实模型错误混在一起。

可以用完全合成的数据做回归：依次喂入 `{"values":[-`、`12]}`，确认中间状态不触发失败或副作用，最终合并为 `{"values":[-12]}` 后才通过校验。再加入真正缺少闭合符号、类型错误和主动中止，确认它们不会被“继续等待”无限掩盖。

## 常见失败与适用边界

最危险的做法有三种：每个 chunk 都执行最终 schema 校验；partial 一变成 `undefined` 就清空页面；流结束时不检查完成状态便写入结果。相反，永远不校验、无限缓冲也会把真实错误拖到更晚。
