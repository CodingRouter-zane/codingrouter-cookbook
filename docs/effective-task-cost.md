# 选模型 API 时，为什么要计算每个有效任务的成本？

资料核实：2026-10-15；工具修订：2026-10-21。类型：常青教程。文中的数字均为虚构算例，不是 CodingRouter 或任何供应商报价。

两个接口的单价不同，最后完成同一项业务的费用也未必按单价高低排列。模型是否需要多轮提示、输出是否能直接使用、失败是否产生账单，都可能改变实际支出。因此采购时可以同时看单价和“每个有效任务成本”。

## 先确定什么叫有效

对于摘要应用，有效任务可以定义为满足字数和关键事实要求的一份摘要；对于客服助手，可以定义为经过抽样审核的合格回复。不能把 HTTP 请求成功直接当成业务成功，也不能在比较不同接口时临时更改评价标准。

LiteLLM 官方提供用量与费用追踪说明，可以作为观察调用成本的一种工具。是否采用它取决于你的部署方式和需要记录的范围。费用记录仍需要和实际账单核对，不能只依靠估算字段。[官方说明](https://docs.litellm.ai/docs/proxy/cost_tracking)

## 一个简单算例

假设相同测试任务中，方案 A 合计花费 12 元，最终得到 80 个合格结果；方案 B 花费 15 元，得到 100 个合格结果。两者每个合格结果都是 0.15 元。这个例子只说明计算方法，不能证明两个真实模型效果相同。

计算式为：测试期内归属于这些任务的实际费用 ÷ 合格结果数量。若合格数量为零，应标记“无法计算”，不能显示零成本。费用应覆盖已计费的重试和追加轮次；但失败请求是否收费、缓存如何计价、图片和音频按什么单位收费，都必须以对应供应商当期规则为准。

## 成本之外还要保留哪些信息

记录模型版本、任务样本、评价规则、参数、测试日期和币种，避免把不同场景的结果放在一起比较。响应速度和稳定性也要单独呈现：一个便宜但无法满足截止时间的结果，对实时业务可能没有价值。人工复核和返工可以另列为运营成本，不要和 API 账单混成无法追溯的数字。

对客户沟通时，可以先约定小规模样本和预算，再给出适合场景及局限。正式报价与测试结果分别标注日期，让客户知道哪些是计费条件，哪些只是一次测试观察。

## 用离线工具复算

仓库已提供[离线有效任务成本计算器](../examples/effective-task-cost/README.md)。先把每个已结束任务的归属费用、币种和是否合格写入 CSV，再运行脚本；结果会按币种分别给出任务数、合格数、总费用和每个合格结果成本。零合格数返回 `null`，不会被误读成零成本；输入不完整、币种混用或金额格式不合规会整批拒绝，不输出部分汇总。

发布前在 Windows 与 Linux 的 Python 3.12.14 环境分别执行了现有 22 项离线测试，样例 CLI 与编译检查通过。工具不联网、不读取 API 密钥，也不会替你判断账单归属、换汇或结果是否合格；Python 3.10+ 是运行前提，但本次未逐版本实测。
